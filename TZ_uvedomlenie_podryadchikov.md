# Техническое задание: система уведомления подрядчиков об ознакомлении с рабочей документацией

## 1. Назначение

Веб-приложение для координаторов ДП (департамента проектирования/подготовки), позволяющее:
- выбрать проект строительства и корпус в его составе;
- прикрепить ссылку на рабочую документацию (Sarex);
- отправить уведомление с просьбой подтвердить ознакомление всем подрядчикам, назначенным на корпус (с возможностью исключить отдельных);
- автоматически контролировать сроки ответа и эскалировать просрочку руководителю проекта;
- если подрядчик не принимает рабочую документацию — сразу уведомлять инициатора и руководителя проекта;
- видеть общую CRM-подобную картину: по каждому корпусу — статус ознакомления по каждой отправленной ссылке и срок, прошедший с момента отправки;
- автоматически классифицировать текст ответа подрядчика (ИИ) и хранить полное содержимое уведомления и ответа с возможностью открыть его прямо из системы.

Отдельно предусматривается канал уведомлений через Telegram-бота — как развитие поверх email-канала (см. раздел 11).

## 2. Роли пользователей

| Роль | Права |
|---|---|
| Координатор ДП | инициирует уведомления по существующим проектам и корпусам, видит статусы уведомлений; справочники видит только для чтения, проекты и корпуса не создаёт |
| Подрядчик | получает письма, отвечает по почте (не заходит в приложение) |
| Руководитель проекта (РП) | получает эскалационные уведомления при просрочке >10 р.д. и уведомления о непринятии РД подрядчиком |
| Администратор | единственный, кто создаёт и изменяет проекты, корпуса, подрядчиков и их привязку к проектам, пользователей и производственный календарь; может также отправлять уведомления |

Подрядчик и РП взаимодействуют с системой только через email — отдельного UI для них не требуется на MVP.

## 3. Модель данных

### 3.1 `projects` — проекты
Проект — объект строительства (например, ЖК или его очередь), по которому выпускается РД. Во всём ТЗ и интерфейсе используется термин "проект".

| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| name | string | наименование проекта |
| address | string | адрес (опционально) |
| project_manager_email | string | email руководителя проекта — адресат эскалации (раздел 4.3) |
| is_active | boolean | активен ли проект |

### 3.2 `corpuses` — корпуса проекта
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| project_id | uuid | FK → projects |
| name | string | наименование/номер корпуса |
| is_active | boolean | активен ли корпус |

Введение отдельной сущности "корпус" нужно, т.к. CRM-доска координатора (раздел 7) строится именно на уровне корпуса: у одного проекта может быть несколько корпусов, и по каждому — свой набор ссылок Sarex и свои статусы ознакомления.

### 3.3 `contractors` — подрядчики
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| name | string | наименование организации |
| email | string | email для уведомлений |
| telegram_chat_id | string \| null | chat_id в Telegram после привязки бота (см. раздел 11) |

Назначение подрядчиков на корпуса — отдельная таблица `corpus_contractors`:

| Поле | Тип | Описание |
|---|---|---|
| corpus_id | uuid | FK → corpuses |
| contractor_id | uuid | FK → contractors |

PK — пара (`corpus_id`, `contractor_id`). Подрядчик назначается на корпус (объект), а не на проект целиком: один подрядчик может работать на нескольких корпусах одного или разных проектов. Назначение — простой список подрядчиков корпуса: договор и вид работ не учитываются. Все подрядчики корпуса по умолчанию получают каждую рассылку по нему (раздел 4.1). Подрядчики проекта — это подрядчики всех его корпусов. Администратор может назначить подрядчика сразу на все активные корпуса проекта.

Изменено 26.09.2026: раньше подрядчики привязывались к проекту (`project_contractors`). При переходе каждый подрядчик проекта назначен на все корпуса этого проекта, лишние назначения администратор снимает вручную.

### 3.4 `notifications` — уведомления (ядро системы)
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| project_id | uuid | FK → projects |
| corpus_id | uuid | FK → corpuses |
| contractor_id | uuid | FK → contractors |
| sarex_link | string | ссылка на РД в Sarex |
| reply_token | string | уникальный случайный код уведомления; из него строится адрес для ответа `rd+<reply_token>@домен` (раздел 4.2), по нему входящее письмо находит своё уведомление |
| initiator_id | uuid | FK → users, кто отправил (координатор) |
| channel | enum | `email`, `telegram` — канал, которым ушло уведомление |
| status | enum | `sent`, `acknowledged`, `has_questions`, `rejected`, `escalated` |

| ai_confidence | float \| null | уверенность модели (0–1), для fallback на ручную разметку при низкой уверенности |
| sent_at | timestamp | дата первичной отправки |
| deadline_at | timestamp | срок ответа: по умолчанию 10 рабочих дней с отправки, координатор может выбрать другой рабочий день при отправке и изменить его позже в карточке; используется для подсветки на CRM-доске (в срок / истекает / просрочено) и для эскалации (раздел 4.3) |
| acknowledged_at | timestamp \| null | дата подтверждения ознакомления |
| rejected_at | timestamp \| null | дата, когда подрядчик не принял РД (раздел 4.2) |
| last_reminder_at | timestamp \| null | дата последнего напоминания |
| reminder_count | int | сколько напоминаний отправлено (0, 1, 2) |
| escalated_at | timestamp \| null | дата эскалации РП |
| message | text \| null | сопроводительное сообщение координатора к рассылке (необязательно); одно на рассылку, копируется в каждое её уведомление; вставляется в первичное письмо и напоминания (раздел 6) |
| needs_manual_review | boolean | флаг "требует ручной проверки": выставляется, если ИИ отнёс ответ к `unclear` (раздел 4.2); снимается, когда координатор вручную задал категорию |

### 3.5 `notification_events` — журнал событий (лог)
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| notification_id | uuid | FK → notifications |
| type | enum | `sent`, `reminder_1`, `reminder_3`, `reply_ack`, `reply_question`, `reply_rejection`, `reply_unclear`, `rejection_notified`, `escalated`, `category_overridden`, `status_changed` (координатор вручную сменил статус), `deadline_changed` (координатор изменил срок ответа) |
| channel | enum | `email`, `telegram` |
| raw_content | text | полный исходный текст письма/сообщения — то, что координатор сможет открыть из системы |
| ai_category | enum \| null | категория, присвоенная ИИ конкретно этому ответу (может отличаться от текущего `notifications.ai_category`, если ответов было несколько) |
| payload | jsonb | прочие метаданные: для исходящих писем — адресаты и состояние доставки (`delivery`: `pending` → `sent` или `failed`, число попыток, последняя ошибка), email-заголовки (`Message-ID` и др.), telegram message_id, для ответов — уверенность и обоснование ИИ и каким классификатором разобран ответ, для ручных действий — кто их сделал |
| created_at | timestamp | |

Отдельная таблица событий нужна, чтобы координатор видел полную историю по уведомлению, а не только текущий статус, и мог открыть исходный текст любого уведомления или ответа (см. раздел 7).

### 3.6 `users` — пользователи системы
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| email | string | логин и адрес для уведомлений координатору (раздел 6, шаблон 4) |
| full_name | string | ФИО |
| password_hash | string \| null | хеш пароля; `null`, если вход через SSO (раздел 8) |
| role | enum | `coordinator`, `admin` |
| is_active | boolean | активна ли учётная запись |

Подрядчики и РП в `users` не заводятся: они работают с системой только через email (раздел 2). На эту таблицу ссылается `notifications.initiator_id`.

### 3.7 `holidays` — производственный календарь
| Поле | Тип | Описание |
|---|---|---|
| date | date | PK, календарная дата |
| is_workday | boolean | `false` — праздник/выходной, `true` — рабочий день, перенесённый на выходной |

Хранятся только исключения из обычной недели. Дата, которой нет в таблице, считается рабочей, если это пн–пт, и выходной, если сб/вс. Пустая таблица означает простое правило "пропускать сб/вс". Таблицу заполняет администратор вручную (раздел 9, решение 6).

## 4. Бизнес-логика

### 4.1 Инициация (координатор)
1. Координатор выбирает проект и корпус, вставляет ссылку Sarex и при необходимости пишет сопроводительное сообщение (например, что изменилось в ревизии или на что обратить внимание).
2. Система показывает всех подрядчиков, назначенных на выбранный корпус (`corpus_contractors`); по умолчанию отмечены все. Координатор может снять отметку с отдельных подрядчиков, чтобы исключить их из этой рассылки.
3. Задаёт срок ответа: по умолчанию подставлена дата через 10 рабочих дней, можно выбрать другой рабочий день (не раньше завтрашнего и не позже чем через год). Срок попадает в письмо.
4. Нажимает "Отправить" → для каждого отмеченного подрядчика создаётся своя запись `notifications` со статусом `sent` и событие `sent` с полным текстом письма; затем каждому уходит отдельное письмо. Если почтовый сервер временно недоступен, письмо остаётся в очереди (`delivery = pending`) и отправляется повторно воркером; после нескольких неудачных попыток — `failed`, координатор видит это в карточке.
5. Если по этому корпусу эта ссылка уже отправлялась, подрядчики, которые её уже получили, по умолчанию не отмечены — повторная отправка только тем, кому ещё не отправляли (например, подрядчику, назначенному на корпус позже).

Все уведомления с одинаковыми `corpus_id` и `sarex_link` образуют одну рассылку: на CRM-доске это одна ячейка (раздел 7.1). Дальше каждое уведомление живёт отдельно: свои сроки, напоминания, ответ и эскалация — каждый подрядчик подтверждает ознакомление сам за себя. Если подрядчика назначили на корпус позже, его можно дослать в ту же рассылку отдельной отправкой.

### 4.2 Обработка ответа подрядчика и ИИ-классификация
Подрядчик отвечает на письмо или на сообщение бота в Telegram. Письма отправляются из почтового ящика системы и принимаются в него же (раздел 9, решение 1): воркер забирает новые письма по IMAP и сопоставляет их с уведомлением по заголовкам `In-Reply-To` / `References` (ссылка на `Message-ID` исходного письма), а если их нет — по адресу ответа вида `rd+<токен>@...`. Вся переписка остаётся в ящике, и её можно смотреть обычным почтовым клиентом.

Каждый входящий ответ прогоняется через ИИ-классификатор (LLM), который относит текст к одной из категорий:

| Категория | Действие системы |
|---|---|
| `acknowledgement` — подтверждение ознакомления | статус → `acknowledged`, `acknowledged_at` = now, событие `reply_ack` |
| `question` / `objection` — вопрос или замечание | статус → `has_questions`, полный текст ответа пересылается инициатору (координатору), событие `reply_question` |
| `rejection` — РД не принята: подрядчик отказывается принимать документацию в работу (например, "не принимаем", "возвращаем на доработку", "в производство работ не допускается") | статус → `rejected`, `rejected_at` = now, событие `reply_rejection`; сразу уходит письмо "РД не принята" (раздел 6, шаблон 5) инициатору и РП проекта (`projects.project_manager_email`), событие `rejection_notified` |
| `unclear` — модель не уверена в категории | статус не меняется автоматически, уведомление помечается флагом "требует ручной проверки" (`needs_manual_review = true`), координатор видит его на CRM-доске отдельным цветом и разбирает вручную |

Для каждого ответа сохраняются: полный исходный текст (`notification_events.raw_content`), присвоенная категория и уверенность модели (`ai_confidence`). Это и есть требование "сохранять уведомление, которое можно открыть из системы" — координатор в карточке уведомления видит не только статус, но и может раскрыть оригинальный текст письма/сообщения и то, как его классифицировал ИИ.

**Порог уверенности:** при `ai_confidence` ниже настраиваемого порога (например, 0.7) ответ автоматически уходит в категорию `unclear`, чтобы не допустить ложного авто-подтверждения ознакомления по неоднозначному тексту. Итоговое решение по таким случаям — за координатором.

**Непринятие РД:**
- Отличие от замечания: замечание или вопрос не отменяют ознакомление и приём РД, их разбирает координатор. Непринятие означает, что подрядчик не может или не будет работать по этой документации, — это уходит и РП.
- Если координатор вручную отмечает ответ как "Не принята" (раздел 7.3), система делает то же самое: статус `rejected` и письмо инициатору и РП. Если ответ ранее был автоматически отмечен как непринятие ошибочно, координатор может переопределить категорию; повторное письмо РП в этом случае не отправляется, а в историю пишется событие `category_overridden`.
- Для `rejected` не отправляются напоминания и эскалация по сроку (раздел 4.3): ответ получен.
- Если после непринятия подрядчик всё же подтверждает ознакомление (кнопкой или ответом), статус меняется на `acknowledged`, событие пишется в историю; инициатор получает уведомление об этом.
- Письмо о непринятии уходит один раз на уведомление; повторные ответы с тем же смыслом только добавляются в историю.

**Рекомендация для MVP:** запускать классификацию через LLM-провайдера (выбрана Qwen3.5 Flash, раздел 9, решение 7) с чётким системным промптом и структурированным JSON-ответом (`category`, `confidence`, `reasoning`), плюс fallback на простой keyword-match, если вызов модели недоступен. Кнопку-подтверждение в письме ("Подтверждаю ознакомление", магическая ссылка) стоит оставить как более надёжный путь параллельно с анализом свободного текста.

### 4.3 Автонапоминания (cron / scheduled job)
Ежедневная задача проверяет все `notifications` со статусом `sent` (без ответа):

- если прошёл 1 рабочий день с `sent_at` и `reminder_count = 0` → отправить напоминание, `reminder_count = 1`, `last_reminder_at = now`, событие `reminder_1`;
- если прошло 3 рабочих дня с `sent_at` и `reminder_count = 1` → отправить повторное напоминание, `reminder_count = 2`, событие `reminder_3`;
- если срок ответа (`deadline_at`) прошёл без ответа → статус → `escalated`, письмо руководителю проекта на адрес `projects.project_manager_email`, событие `escalated`. По умолчанию срок — 10 рабочих дней с `sent_at`, но координатор может задать другой (раздел 4.1) или продлить его (раздел 4.4). Напоминания уходят только до наступления срока.

### 4.4 Ручные изменения координатора
- **Смена статуса** — на CRM-доске (в раскрытом списке подрядчиков ячейки) и в карточке уведомления координатор выставляет статус вручную: `sent` (ожидает ответа), `acknowledged`, `has_questions`, `rejected`; `escalated` ставит только задача напоминаний. Например, подрядчик подтвердил ознакомление по телефону или статус был выставлен ошибочно. Можно оставить комментарий. Флаг `needs_manual_review` снимается. Пишется событие `status_changed`: старый и новый статус, кто изменил, комментарий.
- Ручная отметка «Не принята» отправляет письмо инициатору и РП (раздел 4.2), но только один раз на уведомление: если письмо уже уходило, повторно оно не отправляется. На доске перед отметкой «Не принята» система просит подтверждение.
- **Смена срока** — в карточке уведомления, пока ответа нет (статус не `acknowledged` и не `rejected`). Новый срок — рабочий день позже сегодняшнего. Если уведомление уже эскалировано, после продления статус возвращается в `sent`. Пишется событие `deadline_changed`: старый и новый срок, кто изменил.

Уточнения (26.09.2026):
- задача запускается раз в рабочий день в заданное время (по умолчанию 9:00 по местному времени); выходные и праздники по таблице `holidays` пропускаются;
- если задача пропустила дни (сервер был выключен), подрядчик получает одно напоминание, а не два подряд: сразу второе (`reminder_3`, `reminder_count = 2`);
- напоминание — то же письмо, что и первичное, с пометкой «повторное уведомление», в той же цепочке писем (заголовки `In-Reply-To` / `References` на первое письмо);
- эскалация приходит РП одним письмом на рассылку (корпус + ссылка Sarex): список всех, кто не ответил к сроку, с числом рабочих дней без ответа и ссылками на карточки; событие `escalated` пишется в каждое уведомление;
- уведомления с флагом `needs_manual_review` (ответ ждёт решения координатора) напоминания и эскалацию не получают.

Все интервалы считаются в рабочих днях по таблице `holidays` (раздел 3.7): без записей в ней — простое правило "пропускать сб/вс", с записями — с учётом праздников и переносов по производственному календарю.

## 5. API (пример, REST)

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/projects` | список проектов |
| GET | `/api/projects/:id/corpuses` | корпуса проекта |
| GET | `/api/corpuses/:id/contractors` | подрядчики корпуса |
| POST | `/api/notifications` | создать рассылку и отправить уведомления всем подрядчикам корпуса `{project_id, corpus_id, sarex_link, message?, exclude_contractor_ids?}`; возвращает список созданных уведомлений |
| GET | `/api/notifications` | список уведомлений с фильтрами (проект, корпус, статус, координатор) |
| GET | `/api/notifications/:id` | детали + журнал событий |
| GET | `/api/notifications/:id/events/:eventId` | полный исходный текст конкретного письма/ответа (`raw_content`) |
| GET | `/api/dashboard?project_id=...` | данные для CRM-доски: сетка "корпус × ссылка Sarex", в каждой ячейке сводка по рассылке и статусы по каждому подрядчику |
| POST | `/notifications/:id/status` | ручная смена статуса с доски или из карточки `{status, comment?}` (раздел 4.4) |
| POST | `/notifications/:id/deadline` | новый срок ответа `{deadline}` (раздел 4.4) |
| POST | `/api/webhooks/telegram` | приём входящих сообщений от Telegram-бота (см. раздел 11) |
| GET | `/ack/<токен>` | страница из кнопки «Подтверждаю ознакомление» в письме: показывает, что подтверждается, и кнопку подтверждения. Сама ссылка статус не меняет — почтовые системы (например, защита ссылок в Outlook) открывают ссылки из писем автоматически |
| POST | `/ack/<токен>` | подтверждение ознакомления; токен подписан ключом приложения, повторное подтверждение ничего не меняет |

## 6. Письма (шаблоны)

1. **Первичное уведомление подрядчику** — ссылка на Sarex, сопроводительное сообщение координатора (если заполнено, отдельным блоком с подписью координатора), кнопка "Подтверждаю ознакомление", просьба ответить при вопросах.
2. **Напоминание (1-й/3-й р.д.)** — то же самое, включая сопроводительное сообщение, + пометка "повторное уведомление".
3. **Эскалация РП** — одно письмо на рассылку: проект, корпус, ссылка на Sarex, дата отправки и срок, список подрядчиков без ответа (с количеством рабочих дней без ответа и ссылкой на карточку каждого уведомления).
4. **Вопрос/замечание инициатору** — текст ответа подрядчика + ссылка на уведомление.
5. **РД не принята — инициатору и РП** — проект, корпус, комплект РД и ссылка на Sarex, подрядчик, дата отправки, полный текст ответа подрядчика, ссылка на карточку уведомления. Тема письма начинается с "РД не принята", чтобы его было видно среди остальных.

## 7. Интерфейс координатора

### 7.1 Главный экран — CRM-доска
Ключевое требование: координатор должен видеть общую картину по проекту, а не только плоский список отправленных писем. Главный экран строится как таблица/доска:

- **строки** — корпуса выбранного проекта;
- **столбцы** — отправленные по этому корпусу ссылки Sarex (каждая ссылка = свой цикл ознакомления);
- **ячейка** — сводка по рассылке всем подрядчикам корпуса: сколько ознакомлены из скольких ("Ознакомлены 4 из 5"), полоса со статусами всех подрядчиков и самый тревожный статус в ячейке (приоритет: не принята → требует ручной проверки → просрочено/эскалировано → истекает → есть вопросы → ожидание в срок → ознакомлен);
- клик по ячейке раскрывает список подрядчиков рассылки: у каждого статус (цветовая индикация: ознакомлен / есть вопросы / не принята / ожидание в срок / ожидание — истекает / просрочено-эскалировано / требует ручной проверки от ИИ) и число рабочих дней с момента отправки относительно срока (`deadline_at`); исключённые при отправке подрядчики показаны отдельно;
- клик по подрядчику в списке открывает карточку его уведомления с полной историей и исходными текстами;
- у каждого подрядчика в списке — выбор статуса для ручной смены прямо с доски (раздел 4.4).

Доска фильтруется по проекту, корпусу, подрядчику, статусу и каналу (email/Telegram).

### 7.2 Форма отправки уведомления
Выбор проекта → выбор корпуса → поле ссылки Sarex → сопроводительное сообщение (необязательное, многострочное; в предпросмотре письма видно, как оно будет выглядеть) → список всех подрядчиков выбранного корпуса, все отмечены по умолчанию, можно снять отметку с отдельных → срок ответа (дата, по умолчанию через 10 рабочих дней) → кнопка "Отправить" (с числом уведомлений, которые уйдут).

### 7.3 Карточка уведомления
- журнал событий (кто, когда, что произошло: отправка, напоминания, ответ, эскалация);
- для каждого события — возможность раскрыть исходный текст письма/сообщения (`raw_content`) прямо в интерфейсе, без перехода в почту;
- блок «Решение координатора»: ручная смена статуса с комментарием и изменение срока ответа (раздел 4.4);
- присвоенная ИИ категория и уверенность модели, с возможностью координатора вручную переопределить категорию ("Ознакомлен" / "Вопрос" / "Замечание" / "Не принята") (важно для случаев `unclear` и для дообучения/калибровки промпта в будущем).

## 8. Нефункциональные требования

- Аутентификация координаторов (SSO/логин-пароль — уточнить с ИТ).
- Логирование всех отправленных писем и входящих ответов (для аудита).
- Идемпотентность cron-задачи (не отправлять напоминание дважды при повторном запуске).
- Обработка bounced-писем (неверный email подрядчика) — отдельный статус или алерт координатору.

## 9. Открытые вопросы и принятые решения

### Решения (26.09.2026)

1. **Почта.** Отправка и приём — через один корпоративный почтовый ящик (SMTP для отправки, IMAP для приёма), чтобы все письма системы были видны в обычном почтовом клиенте. Сервис — **Gmail** (изменено 26.09.2026: Microsoft 365 → Google → Mail.ru → Gmail). Подключение по SMTP (`smtp.gmail.com:587`, STARTTLS) и IMAP (`imap.gmail.com:993`, SSL) с паролем приложения: у аккаунта ящика включается двухэтапная аутентификация и создаётся пароль приложения. Ответ подрядчика сопоставляется с уведомлением в первую очередь по заголовкам `In-Reply-To` / `References` (они ссылаются на `Message-ID` нашего письма), plus-адрес `rd+токен@домен` — дополнительно, если почтовый сервис его поддерживает. Поддержка входа в Microsoft 365 через OAuth2 в коде сохранена.
2. **ИИ-классификация через внешний облачный API** — разрешена; провайдер — решение 7.
3. **Данные хранятся на территории РФ (152-ФЗ).** Сервер — российский VPS (раздел 12.3). Последствия, которые нужно закрыть до этапа приёма ответов:
   - ящик Gmail (решение 1) хранит переписку и адреса подрядчиков за пределами РФ — это нужно согласовать с юристом; при переезде на российский сервис (Яндекс 360, Mail.ru) меняются только настройки;
   - LLM для классификации — решение 7; если провайдер модели зарубежный, тексты писем уходят за рубеж — это тоже согласовать с юристом.
4. **Вход в систему** — пока по логину и паролю, SSO позже.
5. **Справочники** (проекты, корпуса, подрядчики) ведутся вручную администратором, без синхронизации с другими системами.
6. **Производственный календарь** (таблица `holidays`) заполняет администратор вручную раз в год по постановлению Правительства.
7. **LLM для классификации ответов — Qwen3.5 Flash** (изменено 26.09.2026, ранее — YandexGPT Lite). Через какого провайдера API подключается модель — уточняется. Если модель недоступна или ответила некорректно — классификация по ключевым словам, как в разделе 4.2.

## 11. Дальнейшее развитие: интеграция с Telegram

Не входит в MVP, но модель данных (`contractors.telegram_chat_id`, `notifications.channel`, `notification_events.channel`) закладывается заранее, чтобы не переделывать схему при добавлении канала.

Планируемая логика:

1. **Привязка подрядчика к боту.** При первом уведомлении подрядчику, помимо email, отправляется (или предлагается) deep-link на Telegram-бота с одноразовым токеном. После перехода и `/start` бот связывает `telegram_chat_id` с записью подрядчика.
2. **Отправка уведомлений через бота** — дублирует или заменяет email по выбору координатора/подрядчика: первичное уведомление, напоминания на 1-й/3-й р.д., информирование об эскалации формируются по тем же шаблонам, что и письма (раздел 6), но в формате сообщений бота с кнопками (например, инлайн-кнопка "Подтверждаю ознакомление" вместо магической ссылки).
3. **Приём ответов** — через `POST /api/webhooks/telegram` (Telegram Bot API webhook); текст сообщения подрядчика проходит через тот же ИИ-классификатор, что и email-ответы (раздел 4.2), результат пишется в `notification_events` с `channel = telegram`.
4. **Единая история** — координатор на CRM-доске и в карточке уведомления видит события из обоих каналов вперемешку, в хронологическом порядке, без разделения на "email-версию" и "telegram-версию" одного и того же уведомления.

Технически: Telegram Bot API + webhook-эндпоинт на бэкенде; хранение `telegram_chat_id` уже заложено в модели данных (раздел 3.3, таблица `contractors`).

## 12. Развёртывание и хостинг

Приложение должно работать на отдельном постоянно доступном сервере, а не на локальной машине координатора. Это нужно для трёх вещей: приём вебхуков от почтового провайдера и Telegram (раздел 11), ежедневный запуск cron-задачи напоминаний (раздел 4.3) независимо от того, включён ли чей-то компьютер, и доступ координатора к CRM-доске (раздел 7) через браузер.

### 12.1 Требования к серверу
Нагрузка минимальна — внутренний инструмент на несколько десятков уведомлений в день, поэтому подходит самый дешёвый вариант VPS:
- 1 vCPU, 1–2 ГБ RAM, 20–25 ГБ SSD — достаточно с запасом для backend + PostgreSQL + reverse proxy на одной машине;
- Ubuntu/Debian LTS;
- статический публичный IP + возможность привязать домен. Домен обязателен: почтовые провайдеры и Telegram Bot API принимают только HTTPS-адрес для вебхуков, голый IP не подойдёт.

### 12.2 Обязательные компоненты на сервере
- Docker + docker-compose — backend, БД и reverse proxy в контейнерах, для воспроизводимого и быстрого повторного деплоя;
- Nginx или Caddy как reverse proxy + Let's Encrypt для бесплатного SSL-сертификата;
- домен (например, `app.company-domain.ru`);
- автоматические бэкапы БД (минимум — ежедневный `pg_dump` в отдельное хранилище: это единственный источник истории по ознакомлению с РД, потеря БД равна потере всей истории уведомлений);
- базовая защита сервера: firewall (открыты только 80/443/22), вход по SSH-ключу с отключённым паролем, автоматические обновления безопасности ОС.

### 12.3 Варианты дешёвых VPS
Сравнить перед покупкой, без привязки к конкретному провайдеру на этапе ТЗ:
Данные хранятся в РФ (раздел 9, решение 3), поэтому только российские провайдеры: Timeweb Cloud, Selectel, REG.RU и аналогичные — минимальный тариф в рублях. Зарубежные (Hetzner, DigitalOcean, Vultr) не подходят.

### 12.4 CI/CD (можно отложить)
Не обязательно на старте MVP, но упрощает дальнейшую жизнь: GitHub Actions workflow, который при мерже в `main` сам подключается к серверу по SSH и разворачивает новую версию (`docker compose pull && up -d` или аналог). Можно добавить отдельным шагом уже после первого ручного разворачивания MVP на сервере.
