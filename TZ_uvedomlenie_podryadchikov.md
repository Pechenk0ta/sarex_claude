# Техническое задание: система уведомления подрядчиков об ознакомлении с рабочей документацией

## 1. Назначение

Веб-приложение для координаторов ДП (департамента проектирования/подготовки), позволяющее:
- выбрать объект строительства и корпус в его составе;
- прикрепить ссылку на рабочую документацию (Sarex);
- отправить подрядчику уведомление с просьбой подтвердить ознакомление;
- автоматически контролировать сроки ответа и эскалировать просрочку руководителю проекта;
- видеть общую CRM-подобную картину: по каждому корпусу — статус ознакомления по каждой отправленной ссылке и срок, прошедший с момента отправки;
- автоматически классифицировать текст ответа подрядчика (ИИ) и хранить полное содержимое уведомления и ответа с возможностью открыть его прямо из системы.

Отдельно предусматривается канал уведомлений через Telegram-бота — как развитие поверх email-канала (см. раздел 11).

## 2. Роли пользователей

| Роль | Права |
|---|---|
| Координатор ДП | создаёт объекты, инициирует уведомления, видит статусы по всем своим уведомлениям |
| Подрядчик | получает письма, отвечает по почте (не заходит в приложение) |
| Руководитель проекта (РП) | получает эскалационные уведомления при просрочке >10 р.д. |
| Администратор | управление справочниками объектов/подрядчиков, доступами |

Подрядчик и РП взаимодействуют с системой только через email — отдельного UI для них не требуется на MVP.

## 3. Модель данных

### 3.1 `objects` — объекты строительства
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| name | string | наименование объекта |
| address | string | адрес (опционально) |
| project_manager_email | string | email руководителя проекта — адресат эскалации (раздел 4.3) |
| is_active | boolean | активен ли объект |

### 3.2 `corpuses` — корпуса объекта
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| object_id | uuid | FK → objects |
| name | string | наименование/номер корпуса |
| is_active | boolean | активен ли корпус |

Введение отдельной сущности "корпус" нужно, т.к. CRM-доска координатора (раздел 7) строится именно на уровне корпуса: у одного объекта может быть несколько корпусов, и по каждому — свой набор ссылок Sarex и свои статусы ознакомления.

### 3.3 `contractors` — подрядчики
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| name | string | наименование организации |
| email | string | email для уведомлений |
| telegram_chat_id | string \| null | chat_id в Telegram после привязки бота (см. раздел 11) |
| object_id | uuid | FK → objects, привязка к объекту (или m2m-таблица, если подрядчик работает на нескольких объектах) |

### 3.4 `notifications` — уведомления (ядро системы)
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| object_id | uuid | FK → objects |
| corpus_id | uuid | FK → corpuses |
| contractor_id | uuid | FK → contractors |
| sarex_link | string | ссылка на РД в Sarex |
| initiator_id | uuid | FK → users, кто отправил (координатор) |
| channel | enum | `email`, `telegram` — канал, которым ушло уведомление |
| status | enum | `sent`, `acknowledged`, `has_questions`, `escalated` |
| ai_category | enum \| null | результат ИИ-классификации последнего ответа: `acknowledgement`, `question`, `objection`, `unclear` |
| ai_confidence | float \| null | уверенность модели (0–1), для fallback на ручную разметку при низкой уверенности |
| sent_at | timestamp | дата первичной отправки |
| deadline_at | timestamp | плановый срок ответа (используется для подсветки на CRM-доске: в срок / истекает / просрочено) |
| acknowledged_at | timestamp \| null | дата подтверждения ознакомления |
| last_reminder_at | timestamp \| null | дата последнего напоминания |
| reminder_count | int | сколько напоминаний отправлено (0, 1, 2) |
| escalated_at | timestamp \| null | дата эскалации РП |
| needs_manual_review | boolean | флаг "требует ручной проверки": выставляется, если ИИ отнёс ответ к `unclear` (раздел 4.2); снимается, когда координатор вручную задал категорию |

### 3.5 `notification_events` — журнал событий (лог)
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| notification_id | uuid | FK → notifications |
| type | enum | `sent`, `reminder_1`, `reminder_3`, `reply_ack`, `reply_question`, `escalated` |
| channel | enum | `email`, `telegram` |
| raw_content | text | полный исходный текст письма/сообщения — то, что координатор сможет открыть из системы |
| ai_category | enum \| null | категория, присвоенная ИИ конкретно этому ответу (может отличаться от текущего `notifications.ai_category`, если ответов было несколько) |
| payload | jsonb | прочие метаданные (email-заголовки, telegram message_id и т.п.) |
| created_at | timestamp | |

Отдельная таблица событий нужна, чтобы координатор видел полную историю по уведомлению, а не только текущий статус, и мог открыть исходный текст любого уведомления или ответа (см. раздел 7).

### 3.6 `users` — пользователи системы
| Поле | Тип | Описание |
|---|---|---|
| id | uuid | PK |
| email | string | логин и адрес для уведомлений координатору (раздел 6, шаблон 4) |
| full_name | string | ФИО |
| password_hash | string \| null | хеш пароля; `null`, если вход через SSO (раздел 8) |
| role | enum | `coordinator`, `admin` |
| is_active | boolean | активна ли учётная запись |

Подрядчики и РП в `users` не заводятся: они работают с системой только через email (раздел 2). На эту таблицу ссылается `notifications.initiator_id`.

### 3.7 `holidays` — производственный календарь
| Поле | Тип | Описание |
|---|---|---|
| date | date | PK, календарная дата |
| is_workday | boolean | `false` — праздник/выходной, `true` — рабочий день, перенесённый на выходной |

Хранятся только исключения из обычной недели. Дата, которой нет в таблице, считается рабочей, если это пн–пт, и выходной, если сб/вс. Пустая таблица означает простое правило "пропускать сб/вс". Как наполнять таблицу — открытый вопрос 3.

## 4. Бизнес-логика

### 4.1 Инициация (координатор)
1. Координатор выбирает объект → система подтягивает список подрядчиков этого объекта.
2. Вставляет ссылку Sarex.
3. Нажимает "Отправить уведомление" → создаётся запись `notifications` со статусом `sent`, письмо уходит подрядчику, событие `sent` пишется в лог.

### 4.2 Обработка ответа подрядчика и ИИ-классификация
Подрядчик отвечает на письмо (reply-to / webhook почтового сервиса) или на сообщение бота в Telegram.

Каждый входящий ответ прогоняется через ИИ-классификатор (LLM), который относит текст к одной из категорий:

| Категория | Действие системы |
|---|---|
| `acknowledgement` — подтверждение ознакомления | статус → `acknowledged`, `acknowledged_at` = now, событие `reply_ack` |
| `question` / `objection` — вопрос или замечание | статус → `has_questions`, полный текст ответа пересылается инициатору (координатору), событие `reply_question` |
| `unclear` — модель не уверена в категории | статус не меняется автоматически, уведомление помечается флагом "требует ручной проверки" (`needs_manual_review = true`), координатор видит его на CRM-доске отдельным цветом и разбирает вручную |

Для каждого ответа сохраняются: полный исходный текст (`notification_events.raw_content`), присвоенная категория и уверенность модели (`ai_confidence`). Это и есть требование "сохранять уведомление, которое можно открыть из системы" — координатор в карточке уведомления видит не только статус, но и может раскрыть оригинальный текст письма/сообщения и то, как его классифицировал ИИ.

**Порог уверенности:** при `ai_confidence` ниже настраиваемого порога (например, 0.7) ответ автоматически уходит в категорию `unclear`, чтобы не допустить ложного авто-подтверждения ознакомления по неоднозначному тексту. Итоговое решение по таким случаям — за координатором.

**Рекомендация для MVP:** запускать классификацию через LLM-провайдера (например, Anthropic API) с чётким системным промптом и структурированным JSON-ответом (`category`, `confidence`, `reasoning`), плюс fallback на простой keyword-match, если вызов модели недоступен. Кнопку-подтверждение в письме ("Подтверждаю ознакомление", магическая ссылка) стоит оставить как более надёжный путь параллельно с анализом свободного текста.

### 4.3 Автонапоминания (cron / scheduled job)
Ежедневная задача проверяет все `notifications` со статусом `sent` (без ответа):

- если прошёл 1 рабочий день с `sent_at` и `reminder_count = 0` → отправить напоминание, `reminder_count = 1`, `last_reminder_at = now`, событие `reminder_1`;
- если прошло 3 рабочих дня с `sent_at` и `reminder_count = 1` → отправить повторное напоминание, `reminder_count = 2`, событие `reminder_3`;
- если прошло >10 рабочих дней с `sent_at` без ответа → статус → `escalated`, письмо руководителю проекта на адрес `objects.project_manager_email`, событие `escalated`.

Все интервалы считаются в рабочих днях по таблице `holidays` (раздел 3.7): без записей в ней — простое правило "пропускать сб/вс", с записями — с учётом праздников и переносов по производственному календарю.

## 6. Письма (шаблоны)

1. **Первичное уведомление подрядчику** — ссылка на Sarex, кнопка "Подтверждаю ознакомление", просьба ответить при вопросах.
2. **Напоминание (1-й/3-й р.д.)** — то же самое + пометка "повторное уведомление".
3. **Эскалация РП** — объект, подрядчик, дата первой отправки, количество дней без ответа, ссылка на карточку уведомления.
4. **Вопрос/замечание инициатору** — текст ответа подрядчика + ссылка на уведомление.

## 7. Интерфейс координатора

### 7.1 Главный экран — CRM-доска
Ключевое требование: координатор должен видеть общую картину по объекту, а не только плоский список отправленных писем. Главный экран строится как таблица/доска:

- **строки** — корпуса выбранного объекта;
- **столбцы** — отправленные по этому корпусу ссылки Sarex (каждая ссылка = свой цикл ознакомления);
- **ячейка** — статус (цветовая индикация: ознакомлен / есть вопросы / ожидание в срок / ожидание — истекает / просрочено-эскалировано / требует ручной проверки от ИИ) и число дней с момента отправки относительно срока (`deadline_at`);
- клик по ячейке открывает карточку уведомления с полной историей и исходными текстами.

Доска фильтруется по объекту, корпусу, подрядчику, статусу и каналу (email/Telegram).

### 7.2 Форма отправки уведомления
Выбор объекта → выбор корпуса → выбор подрядчика(ов) → поле ссылки Sarex → кнопка "Отправить".

### 7.3 Карточка уведомления
- журнал событий (кто, когда, что произошло: отправка, напоминания, ответ, эскалация);
- для каждого события — возможность раскрыть исходный текст письма/сообщения (`raw_content`) прямо в интерфейсе, без перехода в почту;
- присвоенная ИИ категория и уверенность модели, с возможностью координатора вручную переопределить категорию (важно для случаев `unclear` и для дообучения/калибровки промпта в будущем).

## 8. Нефункциональные требования

- Аутентификация координаторов (SSO/логин-пароль — уточнить с ИТ).
- Логирование всех отправленных писем и входящих ответов (для аудита).
- Идемпотентность cron-задачи (не отправлять напоминание дважды при повторном запуске).
- Обработка bounced-писем (неверный email подрядчика) — отдельный статус или алерт координатору.

## 9. Открытые вопросы (уточнить до начала разработки)

2. Нужен ли отдельный личный кабинет подрядчика, или работа только через email — окончательно?

4. Может ли один объект иметь несколько ссылок Sarex одновременно (несколько комплектов РД) — в т.ч. на один корпус?

7. Какой порог уверенности ИИ (`ai_confidence`) считать приемлемым для автоматического статуса `acknowledged`, а какой — требующим ручной проверки координатором.
8. Для Telegram-бота: как происходит первичная привязка подрядчика к его Telegram-аккаунту (deep link с токеном при первом уведомлении, ручной ввод chat_id администратором и т.п.)?
9. Есть ли требование хранить переписку с подрядчиками и их email на территории РФ (152-ФЗ) — влияет на выбор хостинг-провайдера (раздел 12.3: зарубежный vs российский VPS).

## 10. Рекомендуемый стек (для обсуждения)

- Backend: Node.js (NestJS/Express) или Python (FastAPI/Django) — на выбор команды.
- БД: PostgreSQL.
- Очереди/крон: BullMQ / Celery beat / встроенный cron, в зависимости от стека.
- Email: транзакционный сервис (SendGrid, Mailgun, Amazon SES) с поддержкой inbound-парсинга, если нужен парсинг ответов.
- Frontend: React/Next.js.
- ИИ-классификация: вызов LLM API (например, Anthropic Claude) с структурированным JSON-выводом; результат и исходный текст сохраняются в БД, а не только используются "на лету".

## 11. Дальнейшее развитие: интеграция с Telegram

Не входит в MVP, но модель данных (`contractors.telegram_chat_id`, `notifications.channel`, `notification_events.channel`) закладывается заранее, чтобы не переделывать схему при добавлении канала.

Планируемая логика:

1. **Привязка подрядчика к боту.** При первом уведомлении подрядчику, помимо email, отправляется (или предлагается) deep-link на Telegram-бота с одноразовым токеном. После перехода и `/start` бот связывает `telegram_chat_id` с записью подрядчика.
2. **Отправка уведомлений через бота** — дублирует или заменяет email по выбору координатора/подрядчика: первичное уведомление, напоминания на 1-й/3-й р.д., информирование об эскалации формируются по тем же шаблонам, что и письма (раздел 6), но в формате сообщений бота с кнопками (например, инлайн-кнопка "Подтверждаю ознакомление" вместо магической ссылки).
3. **Приём ответов** — через `POST /api/webhooks/telegram` (Telegram Bot API webhook); текст сообщения подрядчика проходит через тот же ИИ-классификатор, что и email-ответы (раздел 4.2), результат пишется в `notification_events` с `channel = telegram`.
4. **Единая история** — координатор на CRM-доске и в карточке уведомления видит события из обоих каналов вперемешку, в хронологическом порядке, без разделения на "email-версию" и "telegram-версию" одного и того же уведомления.

Технически: Telegram Bot API + webhook-эндпоинт на бэкенде; хранение `telegram_chat_id` уже заложено в модели данных (раздел 3.3).

## 12. Развёртывание и хостинг

Приложение должно работать на отдельном постоянно доступном сервере, а не на локальной машине координатора. Это нужно для трёх вещей: приём вебхуков от почтового провайдера и Telegram (раздел 11), ежедневный запуск cron-задачи напоминаний (раздел 4.3) независимо от того, включён ли чей-то компьютер, и доступ координатора к CRM-доске (раздел 7) через браузер.

### 12.1 Требования к серверу
Нагрузка минимальна — внутренний инструмент на несколько десятков уведомлений в день, поэтому подходит самый дешёвый вариант VPS:
- 1 vCPU, 1–2 ГБ RAM, 20–25 ГБ SSD — достаточно с запасом для backend + PostgreSQL + reverse proxy на одной машине;
- Ubuntu/Debian LTS;
- статический публичный IP + возможность привязать домен. Домен обязателен: почтовые провайдеры и Telegram Bot API принимают только HTTPS-адрес для вебхуков, голый IP не подойдёт.

### 12.2 Обязательные компоненты на сервере
- Docker + docker-compose — backend, БД и reverse proxy в контейнерах, для воспроизводимого и быстрого повторного деплоя;
- Nginx или Caddy как reverse proxy + Let's Encrypt для бесплатного SSL-сертификата;
- домен (например, `app.company-domain.ru`);
- автоматические бэкапы БД (минимум — ежедневный `pg_dump` в отдельное хранилище: это единственный источник истории по ознакомлению с РД, потеря БД равна потере всей истории уведомлений);
- базовая защита сервера: firewall (открыты только 80/443/22), вход по SSH-ключу с отключённым паролем, автоматические обновления безопасности ОС.

### 12.3 Варианты дешёвых VPS
Сравнить перед покупкой, без привязки к конкретному провайдеру на этапе ТЗ:
- зарубежные: Hetzner, DigitalOcean, Vultr — от ~$4–6/мес за минимальный тариф;
- российские: Timeweb Cloud, Selectel, REG.RU — сопоставимые тарифы в рублях; имеет значение, если ответ на открытый вопрос 9 требует хранения данных на территории РФ.

### 12.4 CI/CD (можно отложить)
Не обязательно на старте MVP, но упрощает дальнейшую жизнь: GitHub Actions workflow, который при мерже в `main` сам подключается к серверу по SSH и разворачивает новую версию (`docker compose pull && up -d` или аналог). Можно добавить отдельным шагом уже после первого ручного разворачивания MVP на сервере.
