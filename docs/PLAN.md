# План разработки

Приложение для уведомления подрядчиков об ознакомлении с РД. Требования — `TZ_uvedomlenie_podryadchikov.md`, технические решения — `CLAUDE.md`, интерфейс — `mockups/index.html`.

Работа разбита на этапы. Каждый этап — один или несколько pull request'ов в `main`, после каждого приложение собирается и тесты проходят. Размер этапа указан относительно: S — 1–2 дня, M — 3–5 дней, L — около недели и больше (для одного разработчика).

## Этап 0. Решения до начала разработки

Принятые решения записаны в разделе 9 ТЗ (26.09.2026):

| Вопрос | Решение |
|---|---|
| Почта | один ящик Gmail: SMTP для отправки, IMAP для приёма, вход по паролю приложения; вся переписка видна в ящике (26.09: Microsoft 365 → Google → Mail.ru → Gmail) |
| Внешний LLM API | пока разрешён, но см. ограничения 152-ФЗ ниже |
| Хранение данных в РФ | да: российский VPS |
| Вход | логин и пароль |
| Справочники | ведутся вручную |
| Производственный календарь | заполняет администратор вручную |
| LLM для разбора ответов | Qwen3.5 Flash; провайдер API уточняется |

| Вопрос | Что блокирует | Когда нужен ответ |
|---|---|---|
| Ящик Gmail для системы: адрес, двухэтапная аутентификация, пароль приложения | реальная отправка (этап 4), приём ответов (этап 7) | к развёртыванию; до этого письма уходят в Mailpit |
| Через какого провайдера подключать Qwen3.5 Flash (и согласие юриста, если он зарубежный) | этап 7 | до этапа 7 |

## Этап 1. Каркас проекта — S ✅

- `pyproject.toml` на `uv`, зависимости из `CLAUDE.md`; настройки `ruff`, `mypy --strict`, `pytest`.
- Скелет `app/`: `main.py`, `config.py` (все параметры из env), `db.py`, эндпоинт `/health`.
- `Dockerfile` (один образ для `app` и `worker`), `docker-compose.yml` (prod) и `docker-compose.override.yml` (dev) с Postgres и Mailpit — локальным почтовым ящиком, куда в разработке уходят все письма.
- `.env.example` со всеми переменными.
- GitHub Actions: на каждый PR — `ruff`, `mypy`, `pytest` на Postgres в сервис-контейнере.

Готово, когда: `docker compose up` поднимает приложение, `/health` отвечает, CI зелёный.

## Этап 2. Модель данных и рабочие дни — M ✅

- SQLAlchemy-модели по разделу 3 ТЗ: `projects`, `corpuses`, `contractors`, `project_contractors`, `users`, `notifications`, `notification_events`, `holidays`. Первая миграция Alembic.
- `services/workdays.py`: сколько рабочих дней прошло, какая дата будет через N рабочих дней, с учётом таблицы `holidays`.
- Скрипт демо-данных: проект, корпуса, подрядчики и уведомления как в макетах — для разработки и показа.
- Unit-тесты рабочих дней: выходные, праздники, переносы, границы месяца и года.

Готово, когда: миграция применяется на чистую БД, демо-данные загружаются, тесты рабочих дней проходят.

## Этап 3. Вход, общий макет страниц и справочники — M ✅

- Базовый шаблон Jinja2 по макету: шапка, меню, пользователь. Стили переносятся из `mockups/index.html` в `app/web/static/app.css`; все цвета — CSS-переменные в одном блоке `:root`, чтобы смену цветовой гаммы делать правкой только этого блока.
- Вход по логину и паролю, сессия в cookie, роли `coordinator` / `admin`, выход. Первый администратор создаётся командой CLI.
- Экран «Справочники» (макет): проекты и корпуса, назначение подрядчиков на корпуса, подрядчики, пользователи, производственный календарь. Администратор редактирует, координатор только смотрит.
- Тесты: права ролей, валидация форм, нельзя удалить корпус с уведомлениями.

Готово, когда: администратор может завести проект с корпусами и подрядчиками, пользователей и праздники; координатор видит их без права изменения.

## Этап 4. Отправка рассылки — M ✅ (реальная отправка через Gmail — когда будет ящик и пароль приложения)

- Форма «Отправить уведомление» (макет): проект → корпус → ссылка Sarex → сопроводительное сообщение → подрядчики корпуса (все отмечены) → срок ответа.
- `services/notifications.py`: создание рассылки, по одному уведомлению на подрядчика, события `sent`, расчёт `deadline_at`.
- `services/mail/sender.py`: отправка через SMTP; шаблоны писем из раздела 6 ТЗ; у каждого письма свой адрес для ответа, по которому потом находится уведомление.
- Кнопка «Подтверждаю ознакомление»: одноразовая подписанная ссылка, страница «Спасибо, ознакомление подтверждено», событие `reply_ack`.
- Тесты: создание рассылки, исключение подрядчиков, письмо уходит после записи в БД, повторное нажатие на ссылку ничего не ломает.

Готово, когда: координатор отправляет рассылку, письма приходят в Mailpit, нажатие кнопки в письме меняет статус на «Ознакомлен».

## Этап 5. CRM-доска и карточка уведомления — M ✅

- Доска (макет): таблица «корпус × комплект», сводка в ячейке, раскрытие списка подрядчиков через HTMX, счётчики статусов, фильтры.
- Карточка уведомления (макет): сроки, история событий, исходный текст каждого письма и ответа.
- `GET /api/dashboard`, `GET /api/notifications/:id` — те же данные в JSON (раздел 5 ТЗ).
- Тесты: расчёт статуса ячейки («самый тревожный»), «истекает», фильтры.

Готово, когда: по демо-данным доска и карточка выглядят как в макете.

## Этап 6. Напоминания и эскалация — M ✅

- Контейнер `worker` с APScheduler: ежедневная задача в рабочие дни (время — в настройках).
- Только после срока ответа `deadline_at` (изменено 26.09.2026): напоминание подрядчику на 1-й и 3-й рабочий день просрочки, письмо РП на `projects.project_manager_email` в 1-й день просрочки (раздел 4.3 ТЗ).
- Идемпотентность: повторный запуск в тот же день не отправляет второе письмо (`CLAUDE.md`, «Бизнес-инварианты»).
- Тесты с подменой текущей даты: полный цикл «отправка → напоминание → напоминание → эскалация», праздники внутри срока, двойной запуск.

Готово, когда: на демо-данных с подменённой датой приходят правильные письма в правильные дни и только по одному.

Сделано: `services/reminders.py` (правило «что делать сегодня» — чистая функция `next_actions`, покрыта unit-тестами), задача воркера каждый рабочий день в `REMINDERS_HOUR:REMINDERS_MINUTE`, догоняющий запуск после перезапуска днём, ручной запуск `python -m app.scripts.run_reminders`. Напоминание — то же письмо с пометкой «Повторное уведомление, срок истёк» в той же цепочке писем (`In-Reply-To`); после продления срока цикл начинается заново. Эскалация — одно письмо РП на рассылку со списком неответивших; событие `escalated` у каждого уведомления. Если воркер пропустил дни, уходит одно напоминание, а не два подряд.

## Этап 7. Ответы подрядчиков и ИИ-классификация — L

Нужны ящик Gmail с паролем приложения и ключ API провайдера Qwen3.5 Flash (этап 0).

- `services/mail/inbound.py`: воркер раз в несколько минут забирает новые письма из ящика по IMAP, находит уведомление по `In-Reply-To`/`References` (а если их нет — по plus-адресу `rd+<токен>@`), пишет событие с полным текстом и помечает письмо обработанным (не удаляет). Для тестов — почтовый сервер с IMAP в docker (например, GreenMail).
- `services/classifier/`: Qwen3.5 Flash с ответом в JSON и классификация по ключевым словам как запасной вариант, порог уверенности (договорённости — в `CLAUDE.md`).
- До начала этапа: аккаунт у провайдера Qwen3.5 Flash и ключ API.
- Смена статуса по категории, пересылка вопросов координатору, флаг «Требует ручной проверки».
- Непринятие РД по ответу подрядчика: статус «Не принята», письмо инициатору и РП (одно на уведомление). Ручная отметка «Не принята» с письмом уже сделана (см. этап 8).
- В карточке — блок ручного решения (макет): «Ознакомлен / Вопрос / Замечание».
- Недоставленные письма (bounce): отметка у подрядчика и предупреждение координатору.
- Тесты: разбор реальных примеров ответов (подготовить 20–30 обезличенных писем), LLM в тестах подменяется.

Готово, когда: ответ на письмо в Mailpit или тестовом ящике попадает в историю уведомления, классифицируется, а неуверенные случаи видны на доске.

## Этап 8. Развёртывание на сервере — S–M (идёт)

Состояние на 26.09.2026: сервер развёрнут по `deploy/README.md` — VPS с Ubuntu 24.04, вход только по ключу, firewall, Docker, приложение из ветки `stage-8-deploy` по временному адресу `https://194-67-113-53.sslip.io` (HTTPS работает), первый администратор создан, ежедневный бэкап настроен, восстановление проверено. Почта Gmail подключена, тестовое письмо дошло. Рассылка на iCloud отклонялась из-за ссылки на `sslip.io` в письме (`554 5.7.1 [HM07]`), поэтому система переведена на свой домен: **https://rdsarexcheck.online** (REG.RU, DNS `ns1/ns2.reg.ru`, A-запись на сервер), HTTPS работает. Пробная рассылка на iCloud с доменом дошла. Осталось: копия бэкапов вне сервера, внешний мониторинг.

Доработка по итогам первого запуска (26.09.2026): подрядчики назначаются на корпус, а не на проект (таблица `corpus_contractors` вместо `project_contractors`, раздел 3.3 ТЗ). Получатели рассылки — подрядчики выбранного корпуса; миграция назначает прежних подрядчиков проекта на все его корпуса.

Ещё доработки (26.09.2026, раздел 4.4 ТЗ): координатор сам выбирает срок ответа при отправке и может продлить его в карточке; статус меняется вручную на доске и в карточке («Ожидает ответа / Ознакомлен / Есть вопросы / Не принята», с комментарием), каждое изменение — событие в истории; ручная «Не принята» отправляет письмо инициатору и РП.


- Покупка российского VPS (1 vCPU, 1–2 ГБ RAM: Timeweb Cloud, Selectel, REG.RU и т.п.) и домена, настройка DNS.
- Ящик системы в Gmail: двухэтапная аутентификация, пароль приложения, IMAP включён.
- Защита сервера: firewall (80/443/22), вход только по SSH-ключу, автоматические обновления безопасности.
- `docker compose up -d` с Caddy (HTTPS автоматически), `.env` на сервере.
- Ежедневный бэкап БД во внешнее хранилище и **проверенное восстановление** из него.
- Простой мониторинг доступности (внешняя проверка `/health` с уведомлением).
- Инструкция по деплою и откату в `deploy/README.md`.

Готово, когда: приложение открывается по HTTPS, письма доходят до реальных ящиков и не попадают в спам, бэкап восстановлен на тестовую БД.

## Этап 9. Пилот — 2–4 недели

- Один проект, 1–2 координатора, реальные подрядчики.
- Собираем: письма, которые ИИ классифицировал неверно или неуверенно (для настройки промпта и порога), пожелания к доске и письмам.
- Исправления по итогам пилота, затем подключение остальных проектов.

## После пилота

- CI/CD: автоматический деплой при мерже в `main` (раздел 12.4 ТЗ).
- Telegram-бот (раздел 11 ТЗ): привязка подрядчика, отправка, приём ответов.
- Смена цветовой гаммы — правка CSS-переменных в `app/web/static/app.css`.
- По запросу: синхронизация справочников с другой системой, SSO, отчёты и выгрузки.
